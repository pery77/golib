# Roadmap

Milestones land in order; what goes into each one can still move as we learn. The "Project status" table in [AGENTS.md](../AGENTS.md) mirrors this file, so update both together.

## M0: Foundation (done, 2026-09-14)

- Cross-platform `golib` CLI entry points with `setup`, `doctor`, `clean` and `help`.
- VS Code workspace: recommended extensions, editor settings, tasks.
- AI instructions: `AGENTS.md`, `CLAUDE.md`, Claude Code settings and the `/make-game` skill.
- Docs: vision, roadmap, architecture, tooling, contributing, game-making playbook.

## M1: Toolchain and first window (done, 2026-09-14)

- `golib setup` downloads Go 1.27.1 into `.tools/`, verifying its checksum.
- raylib 6.0 through [raylib-go](https://github.com/gen2brain/raylib-go) in its purego mode, so no platform needs a C compiler. The prebuilt raylib library ships inside the binding's module; `golib` extracts it into `.tools/raylib/` and copies it next to each build (see [tooling.md](tooling.md)).
- The framework and game split (see [architecture.md](architecture.md)). `framework/` is the Go module `golib`, and `games/hello` opens a window and draws text through it. In M2, `games/platformer` replaced it as the test game.
- `golib run`, `golib build` and `golib test`, with the game picked by its folder name, plus `golib go` to run the project's Go toolchain.
- VS Code: the Go extension uses the local toolchain, and "GoLib: debug game" (F5) debugs a game with Delve.

Known gaps, written down as the [definition of done](contributing.md#definition-of-done) requires:

- On hold since 2026-09-15, while Windows comes first, and partly closed on 2026-09-18: two other people ran GoLib on their own Linux and macOS machines for the first time. `golib.sh` and `tools/cli` set up the project, built a game, ran it and made a `golib dist` build that played from its unzipped folder, with no problems reported. Framework features since M1 have still only been tried on Windows, and nobody has reported `golib doctor` on those platforms, nor `golib test` or `golib shot` on Linux; on 2026-10-04 both ran on macOS (see [Other platforms](#other-platforms-on-hold)). From Windows, its help, usage errors and doctor ran in Git Bash, and its Go download, checksum check and extraction ran on a simulated Linux. Continuous integration on Linux and macOS runners would keep it working.
- VS Code's Go extension runs `go version -m` without the project environment each time it starts, so Go updates its local telemetry counters in the user's config folder. No setting redirects those calls; see [tooling.md](tooling.md#vs-code-integration).

## M2: Framework basics (done, 2026-09-16)

- Done: a fixed-step game loop. `Update` runs 60 times per second of game time with a constant `dt`, whatever the frame rate; after a long pause the lost time is skipped.
- Done: scenes. Each scene is a `golib.Game`, and `golib.SwitchScene` moves between them; `games/platformer` has a title, play, pause and won scene.
- Done: input from the keyboard, the mouse (pointer, buttons, wheel) and up to four gamepads (buttons, and sticks with a dead zone), with each press, click and wheel turn delivered to exactly one update. Not covered: analog trigger pressure, vibration.
- Done: random numbers with `golib.RandomInt` and `golib.RandomFloat`, and `golib.SetRandomSeed` to repeat them.
- Done: the GoLib window, `golib-ui.cmd`: a button for each `golib` command, with its output, for people who prefer clicking. Windows only; on Linux and macOS, use the CLI or the VS Code tasks.
- Done: `golib.Quit` ends a game. No key quits on its own: raylib's default of closing on Esc is turned off.
- Done: 2D drawing with rectangles, circles, lines, triangles, text, and `Rectangle` overlap and point checks. Textures and sprites are part of M4.
- Done: the screen scales to any window size and to fullscreen (`golib.SetFullscreen`), with `Config.PixelArt` for sharp pixels, and post-processing shaders run over the whole picture (`golib.NewShader`, `golib.SetPostProcess`). `games/asteroids` tries them out.
- Done: sound effects made in code, so a game ships no sound files. `golib.NewSound` turns a `golib.SoundSpec` (waveform, frequency, pitch slide, duration, attack, release, volume, duty, vibrato) into a sound raylib plays, with ready-made recipes (`golib.Laser`, `golib.Explosion`, `golib.Pickup`, `golib.Jump`, `golib.Hurt`, `golib.PowerUp`) and `golib.SetVolume`. Up to four copies of a sound play at once. `games/asteroids` uses them. Not covered: looping or positional sounds, and sound effects loaded from files, which are part of M4.
- Done: music streamed from the game's `assets/` folder with `golib.NewMusic`: OGG, MP3, WAV, QOA and the tracker formats XM and MOD, but not IT, which raylib doesn't read. It loops, and `golib.Music` has `Play`, `Pause`, `Stop` and `SetVolume`. `games/asteroids` plays a module. Not covered: crossfading and playlists.
- Done: reading files from the game's `assets/` folder with `golib.ReadAsset`, from disk in debug builds and from the copy embedded in dist builds.
- Done: `golib new <name>` creates a game folder in `games/` from `tools/template/game/`, ready to run, without touching the framework.
- Done: example games that double as documentation. `games/platformer` tries each feature as it lands, and `games/asteroids` shows screen effects, fullscreen, sound and music; both keep growing with the framework.
- Done: an API guide for agents, `framework/README.md`: every exported name grouped by task, the rules the names don't tell you, and what GoLib doesn't have yet. Two framework tests fail when it misses an exported name or names one that doesn't exist. They embed the guide, so `go test` runs them again when only the guide changes.

## M3: Agent verification loop (done early, during M2, 2026-09-15)

- `golib shot` runs a game in a hidden window for a number of frames and saves screenshots an agent can inspect, and `--input` plays keys, mouse buttons and mouse moves in chosen updates, so shots reach every scene.
- Deterministic runs, so results are reproducible: the fixed timestep, with exactly one update per frame in shots, and random numbers that start from the same seed in every shot.

## M4: Content (done, 2026-09-17)

Postponed on 2026-09-15, resumed on 2026-09-17. Loading what Aseprite, Tiled and audio tools make, through `golib.ReadAsset`:

- Done on 2026-09-17: sprites. `golib.NewSprite` reads a PNG image as one frame, or an Aseprite file (`.aseprite`, `.ase`) with its frames, and `golib.NewSpriteSheet` cuts a PNG image into a grid of frames. `Screen.DrawSprite` draws a frame, flipped, scaled, rotated around an origin or tinted, without smoothing, and `golib.Animation` says which frame shows after a time, looping or once; Aseprite tags become animations, with their direction, repeat count and frame durations. Aseprite files are combined as Aseprite 1.3 combines them: visible layers, opacity, all 19 blend modes (with Aseprite's own 8-bit math), groups, linked cels, z-indexes, and indexed and grayscale sprites. `framework/testdata/aseprite/make.lua` has Aseprite 1.3.18 make test files and draw each frame, and the tests match those pictures pixel for pixel; so did the 492 frames of 16 files from a texture pack. Frames of a sprite go into one texture. A missing file, a frame or animation a sprite doesn't have, or any other mistake with an asset now stops `Run` with an error, including mistakes made before `Run` started.
- Not covered: tilemap layers and slices in Aseprite files, parts of a PNG image that aren't on a grid, and groups that Aseprite combines on their own first, which no test file has yet (Aseprite 1.3.18 doesn't write them by default).
- Done on 2026-09-17: 2D maps from Tiled. `golib.NewMap` reads a TMX map with its TSX tilesets, TX templates and PNG images: tile layers (CSV, XML or base64 data, uncompressed or compressed with zlib or gzip), object layers, image layers and groups, image tilesets with margins and spacing, collections of images, animated tiles, flipped and rotated tiles, tile offsets, object alignment, infinite maps, custom properties (with class members) on maps, layers, tiles and objects, and the older `type` attribute. `Screen.DrawMap` and `Screen.DrawMapLayer` draw tile layers, image layers (repeated or not) and tile objects, with visibility, opacity, tint colors, offsets, parallax factors, the draw order of object layers and the map's render order and background color, only for the tiles on the screen and at whole pixels. `Map.Tile`, `Map.TileAt`, `Map.TilesIn`, `Map.Objects`, `Map.Object` and the `Properties` methods tell the game what is where. Checked against Tiled 1.11's `tmxrasterizer --no-smoothing`: Tiled's example maps desert, orthogonal-outside and perspective_walls, and a map with every flip of three tiles, match pixel for pixel; sewers differs by up to 3 levels where layers are half transparent, and sticker-knight only along the see-through edges of its pictures and a rotated object. Mistakes such as a missing file, a JSON map, an isometric map, Zstandard data or a layer the map doesn't have stop `Run` with a message that says what to change in Tiled.
- Parallax follows Tiled's documentation: a layer is in place when the view's center is at the map's parallax origin. The code of Tiled 1.11's editor adds the origin to the view's center instead, a sign change made in a 2024 refactor, so a map that sets a parallax origin may look different in Tiled's editor; maps that leave it at 0, 0 look the same.
- Not covered in maps: isometric, hexagonal and staggered maps, Tiled's JSON files, Zstandard data, collision shapes drawn on tiles in the tileset editor, and drawing object shapes and text.
- Done on 2026-09-17: sound effects from files. `golib.NewSoundFile` reads a `.wav`, `.ogg`, `.mp3` or `.qoa` file from the assets folder into a `golib.Sound`, which plays like the sounds made in code, up to four copies at once. The file is read the first time the sound plays, even without a sound device, so a missing or unreadable file stops `Run` under `golib shot` too. `Sound.SetVolume` sets one sound's volume, for files and for sounds made in code. A test opens the sound device, silent, and plays WAV and QOA files; raylib can't write OGG or MP3 files to test with, so those were only tried with a broken file, which raylib's OGG reader rejects. FLAC is off in raylib-go's build. Not covered: looping, stopping and positional sounds.
- Done on 2026-09-17: sound effects designed in jfxr (see [Decisions](#decisions)). `golib.NewSoundFile` also reads the `.jfxr` files that [jfxr](https://jfxr.frozenfractal.com), a sound effect maker in the browser, saves, and makes the sound from their settings with `framework/jfxr.go`, a Go version of jfxr's synthesizer at commit e971e4c (the synthesizer last changed in 2019): ten waveforms, an envelope with punch and tremolo, pitch sweeps, repeats, two pitch jumps and vibrato, up to five harmonics, a flanger, bit crush, low-pass and high-pass filters, each with its sweep, compression, normalization and amplification. `framework/testdata/jfxr/make.go` runs jfxr's own code, downloaded and checked, in Edge or Chrome with no window: it saves a sound from each of jfxr's eight presets, from fixed seeds, and exports every test sound as jfxr exports WAV files. The tests match those 20 files sample for sample on Windows amd64, also when built with `GOAMD64=v3`, which lets Go fuse multiplications with additions. Settings out of range are kept in range, as jfxr keeps them, and anything jfxr wouldn't write stops `Run` with a message. jfxr is under the BSD 3-Clause license, so `golib dist` adds `framework/LICENSE-jfxr.txt` to every game's `THIRD-PARTY-LICENSES.txt`. `games/platformer` plays its chest sound from `assets/sounds/chest.jfxr`. Not covered: jfxr's preset, randomize and mutate buttons, which only matter in jfxr. Not tried on arm64, where the code keeps multiplications and additions apart, as JavaScript does.
- Done on 2026-09-17: fonts. `golib.NewFont` reads a `.ttf` or `.otf` file, and `Screen.DrawText` and `Screen.TextWidth` take a `golib.TextOptions` with the font; without one they keep the built-in font. raylib draws a font's letters into a texture at one size, so GoLib makes one texture per size the game uses, the first time it uses it, and keeps the last eight per font, flushing raylib's pending drawing before it frees one. Every size starts with ASCII, and any other letter is added the first time it is drawn, so text in any language works with a font that has its letters. The file's table directory is checked before raylib reads it, because raylib's font reader trusts its input. Text is now drawn at whole pixels, with the built-in font too. Tests draw with a TrueType font the test builds itself, in a hidden window; tried by hand with Arial, Consolas, Spanish and Japanese text. Not covered: font collections, WOFF, bitmap fonts (`.fnt`, `.bdf`), letter and line spacing, and hinting, so small sizes look a little tight, as in raylib.
- Done on 2026-09-17: the window of a pixel art game (`Config.PixelArt`) opens as many whole times larger than its screen as fits in four fifths of the monitor, and centered, so a 320 by 180 game opens at 1280 by 720 on a 1920 by 1080 monitor instead of in a tiny window.
- Done on 2026-09-17: sprites are drawn at whole pixels, as maps and text are: a sprite half a pixel off repeated one column of its pixels. The framework tests that draw now share a hidden window, opened on a locked thread.
- Done on 2026-09-17: `games/platformer` uses the new content: the forest sprite sheets on a 320 by 180 pixel art screen, a Tiled level that scrolls, with parallax, tile properties and objects, and animations for the hero and the snakes. It still makes its sounds in code, since it has no sound files of its own (its chest sound later came from a `.jfxr` file, above), and uses the built-in font.

## M5: Shipping (done on Windows, 2026-09-17)

Closed on 2026-09-17 for Windows, which comes first; the rest of shipping waits in [Other platforms](#other-platforms-on-hold).

- `golib dist`. Done early, during M2, as a single executable with raylib, libffi and the game's assets inside; on Windows it opens no console window and shows errors in a message box. Since 2026-09-17 it is a folder and a zip (below).
- Done on 2026-09-17: the CLI in Go. The command logic moved from the twin scripts into one Go program, `tools/cli`, one command at a time (see [Decisions](#decisions) and [tooling.md](tooling.md#the-go-program)):
  - `dist`, with `tools/shipping` folded in. The scripts build the program into `build/golib/` and start it with the user's environment, and it sets GoLib's environment for the `go` commands it runs. It now checks `game.json` and `icon.png` on Linux and macOS too, and prints a game's title correctly when it isn't ASCII. On Windows, its executables match the ones the script made, byte for byte, apart from Go's build information.
  - `new`, `build`, `run`, `shot` and `test`. Their output is the same as before, their screenshots match the scripts' byte for byte, and games now start without GoLib's Go variables or any `GOLIB_SHOT_` variable from the user's environment. The scripts shrank from about 800 lines each to about 450, and keep `help`, `setup` up to installing Go, `doctor`, `clean` and `go`, which has to work when `tools/cli` doesn't compile.
  - `setup` after Go is installed: downloading the Go modules and filling `.tools/raylib/`, which now has one implementation. The scripts pass on how many warnings they printed, so the summary counts them. A setup from scratch, in a copy of the project with no `.tools/`, took 37 seconds, and `test`, `shot` and `dist` then worked there without writing to the user's Go telemetry folder.
- Done on 2026-09-17: dist builds as a folder, `build/<game>/dist/<game>/`, with the executable, raylib and libffi side by side, and a `THIRD-PARTY-LICENSES.txt` with the licenses of Go, of each Go module in the game but GoLib (purego, raylib-go and ffi), of raylib and libffi, and the game's `assets/ATTRIBUTION.md`; plus a zip of that folder to share, `<game>-<version>-<os>-<arch>.zip`, instead of one executable that writes the libraries into the player's cache folder (see [Decisions](#decisions) and [tooling.md](tooling.md#dist-builds)). The executable still carries the game's assets. Tried on Windows amd64: unzipped anywhere, the game runs from its folder and writes nothing into the player's cache folder. Built for Linux amd64 from Windows, the executable has `$ORIGIN` as its `DT_RUNPATH`, which should make Linux find `libraylib.so.6.0.0` next to it; on 2026-09-18 a dist build made on someone else's own Linux machine played from its unzipped folder, and so did one made on macOS. macOS dist builds still carry both libraries: macOS looks for a library given by its bare name, as raylib-go gives raylib's, only in `DYLD_LIBRARY_PATH`, the working directory and system folders.
- Done on 2026-09-17: the notices of the libraries inside raylib, which raylib's `LICENSE` doesn't cover. raylib-go's `config.h` and C files include cgltf, tinyobj_loader_c, vox_loader, m3d, par_shapes, QOI, QOA and glad, and, in the Windows library, dirent; their strings are in the prebuilt Windows, Linux and macOS libraries. Their notices, copied from their headers, are in `tools/cli/notices/raylib-6.0.txt`, which `dist` adds under raylib's heading, and `golib test` fails when raylib-go brings a raylib version without such a file (see [tooling.md](tooling.md#third-party-licenses)). The others (GLFW, miniaudio, dr_libs, stb, jar_xm, jar_mod, sinfl, sdefl, rprand, rl_gputex) are zlib, public domain, MIT-0 or a choice of public domain, which ask for nothing in programs. Not a legal review: whoever publishes a game should still check what they ship.
- Done: the Windows icon and version information. `golib dist` reads the game's `icon.png` and `game.json` (title, version, author, copyright), and `tools/shipping`, GoLib's first piece of tooling written in Go, turns them into Windows resources that the Go linker adds to the executable. Explorer, the title bar and the taskbar show the icon, and Explorer and Task Manager show the details. `golib new` writes a `game.json`, and both example games have both files; their icons are placeholders drawn in code, to be replaced with ones made in Aseprite.
- Done on 2026-09-17: debug builds from `build`, `run` and `shot` carry the icon and the details too, so the game's window and taskbar button show its icon while it is being made. They say nothing about the two files unless one has a mistake, which stops the build as it stops `dist`. The resource file next to `main.go` is now `golib_windows_<arch>.syso` for both kinds of build.
- Done on 2026-09-17: a Windows game that can't load raylib or libffi says so. raylib-go and ffi load them while Go initializes their packages, before any GoLib code runs, so a dist build moved out of its folder used to end with no message. The framework's `golib/internal/startup` package loads them first, which works because Go initializes packages in import path order and it imports only `syscall` and `unsafe`; when one doesn't load, it writes `cannot load library <name>: <reason>` and where the libraries go, shows it in a message box in dist builds and in debug builds started from Explorer, and exits with code 1 (see [tooling.md](tooling.md#libraries-that-dont-load)). Tried with the platformer's dist executable alone in a folder: the message box named both libraries. `golib.Run` now decides whether to show its errors in a message box the same way, by asking whether anyone shares the game's console.
- Done on 2026-09-17: golib keeps working on Windows while a game it started is open (see [tooling.md](tooling.md#the-go-program)). `golib.ps1` builds and starts `golib-2.exe`, and so on, when `golib.exe` is running; debug builds copy the libraries only when they changed, so `build` and `shot` work while `run` has the game open (tried); and `clean` says which folder it couldn't delete and why, in both scripts, instead of a PowerShell error.

Known gaps, on Windows:

- `golib clean` can't delete `build/` while a game golib started is open; it says so and exits with code 1.
- A debug build fails if the game was built again while both older copies of it are still open: `go build` moves only one running executable aside.
- A library that loads but is the wrong one, such as a `raylib.dll` of another raylib version next to the executable, still makes raylib-go panic before `golib.Run`, with no message in a dist build.
- F5 builds, which the Go extension makes, don't carry the icon.
- The example games' icons are placeholders drawn in code.

## Other platforms (on hold)

On hold since 2026-09-15: Windows comes first, and the owner doesn't prioritize the rest for now. Gathered here on 2026-09-17 from the milestones above, for when it resumes:

- Linux and macOS: `golib.sh` and `tools/cli` ran on real machines for the first time on 2026-09-18, on two other people's computers, where setup, a build, a run and an unzipped `golib dist` build all worked. Nobody has reported `golib doctor` there, nor `golib test` or `golib shot` on Linux (both ran on macOS on 2026-10-04: see below), no GoLib machine runs either system, and the framework's own features have only been tried on Windows. Continuous integration on Linux and macOS runners would keep it working.
- macOS window, fixed on 2026-09-25 after a game was played on a Retina iMac (Intel, macOS 26): the window opened measured in Retina pixels, so only the bottom-left quarter of the screen showed until the player resized it, and fullscreen, a borderless window, sat below the menu bar with its bottom off the monitor. `raylib_darwin.go` now makes raylib measure the window again as it opens, and fullscreen on macOS is the system's own. macOS loses every key and mouse event while that fullscreen slides in or out, so the Enter that asked for it stayed down until pressed again; the switch now waits until nothing is held. Not yet tried on Apple silicon or on a monitor without Retina.
- Dist builds have been tried on Windows amd64, and on 2026-09-18 on someone else's Linux and macOS machines, whose architectures weren't recorded. On Linux, players also need the system's `libffi.so.8`, `libX11.so.6` and `libGL.so.1`.
- macOS: loading raylib and libffi from inside the app. Since 2026-09-26 `golib dist` wraps the executable in an app, `<title>.app`, with the game's icon and details, signed ad hoc, and debug builds show the icon in the Dock; tried on an Intel Mac, not on Apple silicon, and not yet downloaded and opened on another Mac. raylib-go and ffi would need a way to take a full path, such as `@executable_path/libraylib.6.0.0.dylib`; ffi reads its library's name from a package variable that `-ldflags=-X` can set, but raylib-go has none. Until then, macOS dist builds write raylib and libffi into the player's cache folder, with the problem the decision below describes.
- Builds for other platforms than the current one: `dist` builds for the machine it runs on.
- The icon and the details on Linux: its dist builds check `icon.png` and `game.json` but don't use them.
- Windows on ARM: the ffi module ships libffi for Windows amd64 and macOS only, so games would stop at startup, in debug and dist builds alike (the startup check would at least say that `libffi-8.dll` is missing). The icon resources have been linked and read back by Windows, but not seen in a running game. Not tested.
- The GoLib window, `golib-ui.cmd`, is Windows only; on Linux and macOS, people use the CLI or the VS Code tasks.
- Web build: no longer on hold, and no longer a platform port; see [Web build](#web-build-started) below.
- The window's monitor, size and frame rate cap (`golib.SetMonitor`, `golib.SetWindowSize`, `golib.SetFrameRate`), added on 2026-09-30, were tried on macOS with one monitor only: moving to another monitor, in a window and in fullscreen, and macOS leaving its fullscreen to move and entering it again, are untried, as is all of it on Windows and Linux. `golib.DisplayScale` was tried on a Retina iMac only; on Windows and Linux it says 1, since they measure windows in pixels, which a Linux desktop on Wayland with scaling may not.
- `golib test` on macOS, fixed on 2026-10-04 on an Intel Mac (macOS 26), where it had never passed. Every module that loads raylib failed: the go command, signed with the hardened runtime, loses `DYLD_LIBRARY_PATH` for the test binaries it starts, so they couldn't load libffi. Once they could, the framework's window tests stopped the test program, because macOS opens windows only on the main thread and go test runs tests on others. `golib test` now starts each test binary through `/usr/bin/env` with the variable, and the framework's tests open, draw in and close their windows on the main thread (see [tooling.md](tooling.md#raylib-libraries)). There, every module passes, the framework's ten window tests included, twice in a row; `golib shot`, on the desktop and with `--web`, worked too. Untried on Apple silicon. Still on macOS: `golib go test` and `golib go run` lose the variable the same way, and test results aren't cached.
- Building while the game runs on Linux and macOS, fixed on 2026-09-30 by a contributor who hit it: `go build` refused to link onto the executable `golib run` had open ("text file busy"), so `build` and `shot` failed until the game was closed. `buildGame` now links to `.<game>.new` beside it and renames that over the old one, which a running game survives (see [tooling.md](tooling.md#the-go-program)). Windows keeps its own way; `golib test` passes there with the change. Which system the fix was tried on wasn't recorded.

## M6: 2D essentials (done, 2026-09-18)

Added on 2026-09-17, before 3D, which became M7 (see [Decisions](#decisions)). What nearly every 2D game needs and GoLib doesn't have yet, from the list of what is missing in [framework/README.md](../framework/README.md#what-golib-doesnt-have-yet):

- Done on 2026-09-17: test games. Two agents each made a game from a single prompt, as someone with the template would, and wrote down what they missed: `games/skyraid`, a top-down shooter in an arena larger than the screen, with waves, and `games/crates`, a Sokoban with ten Tiled levels, music and saved progress. Both play, pass their tests and look right in shots. What they found, most costly first:
  - No camera or vector math: about 330 of skyraid's 2,060 lines, and `games/asteroids` already had copies of some of it.
  - No saved data: crates chose its own save folder, with build tags for dist builds, and read `GOLIB_SHOT_DIR` so that shots repeat; `golib dist` still tells players the game writes nothing to their machine.
  - No looping or stopped sounds, and no way to have music without a file: crates plays a tune note by note with `golib.NewSound` (187 lines), and skyraid has no engine sound.
  - Drawing helpers every game writes again: centered text, outlined rectangles and circles, polygons and rotated shapes, a color with another opacity. skyraid also missed additive blending for glows, and hiding the mouse pointer (it called raylib).
  - No way to tell that the pointer moved, so menus that follow the pointer tracked it by hand; the platformer's menu picked the button under a resting pointer when it opened.
  - For agents: `golib test` couldn't test one game, and another game in progress failed it; `golib shot` can't start from a chosen state, such as wave 5, so skyraid edited its code for a while; pixel art shots are small to look at; the `[info]` line of `shot` repeated a whole `--input` script; `golib run` printed -1 as 4294967295.
  - In the template and the docs: the template's world was the screen's size, moved faster diagonally, and kept its colors where the reference game doesn't; the playbook doesn't say what to do when a user wants music but gives no file, or wants Tiled levels with no tileset art, or that puzzle levels need a test that solves them; the list of what GoLib lacks missed several of these.
- Done on 2026-09-17: vectors and a 2D camera (see [framework/README.md](../framework/README.md#camera)). `Vector2` has `Add`, `Sub`, `Scale`, `Length`, `Distance`, `Dot`, `Normalize`, `ClampLength`, `Angle`, `Rotate`, `MoveTowards` and `Lerp`, with angles in degrees as for sprites, plus `golib.Vector2FromAngle` and `Rectangle.Center`. `golib.NewCamera` makes a `Camera` that follows `Target` with an optional `Lag`, zooms, stays inside `Bounds`, shakes, and turns points between the world and the screen (`ToWorld`, `ToScreen`, `View`); `Screen.SetCamera` draws through it, with raylib's 2D camera, and `DrawMap` then culls tiles and moves parallax layers by the camera's view. The view sits on whole screen pixels. A test draws a map and shapes through a camera and with offsets, and gets the same pixels; `games/platformer` now uses the camera, and its shots are byte for byte the same as before; `games/skyraid` followed later, losing 110 lines of its own camera, vector maths and shape drawing. Not covered: rotating the camera.
- Done on 2026-09-17: `Input.MouseMoved`, also under `golib shot`; the platformer's menu uses it, and no longer picks the button under a resting pointer.

## M7: 3D (planned)

Planned on 2026-10-20 as a full 3D engine inside GoLib, for good-looking 3D games, in place of its first scope, which was glTF models, a 3D camera and basic lighting. The reasons, and the principles it changes, are in [Decisions](#decisions). Stages 0 to 4 are built, below. Each stage lands on its own, on the desktop and in the browser at once, with its tests and its docs, and every 2D game's screenshots stay byte for byte what they were.

The shape of it:

```text
game       the 3D API: small, with working defaults, and lower-level access for what it doesn't cover
golib      the 3D engine, plain Go: math, scene, glTF reader, materials, renderer, animation, collisions
device     a GPU contract of about 30 functions: buffers, textures, framebuffers, shaders, draws
  raylib   OpenGL 3.3, called directly through the pointers raylib's loader found
  web      WebGL 2, through the 2D's command buffer
```

The engine uses nothing of raylib's 3D: not its models, its animations, its default shaders or rlgl's drawing. So the engine is written once, its shaders are GoLib's own on both backends (the web one turns them into GLSL ES with `device.ESShader`, as it does for post-processing), and skinning needs no custom raylib build. The design, the measurements behind it and the conventions are in [3d.md](3d.md).

- Done on 2026-10-20: stage 0, the spike, the measurements and the directives. The directives were rewritten the same day (see [Decisions](#decisions)). A private game drew Sponza, the glTF test scene from Khronos (103 draws, 262,267 triangles, 69 textures), and grids of up to 100,000 cubes, through a glTF reader of about 350 lines in Go, a minimal renderer and two GPU layers of about 400 lines each, one on OpenGL and one on WebGL 2, on an iMac with an AMD Radeon Pro 5300 and in headless Chrome on the same machine.   - rlgl is not the way down: its indexed draws take 16-bit indices only, the binding lacks `rlLoadTexture`, and its calls go through libffi at 120 ns. OpenGL called directly, through `rlGetProcAddress` and `purego.SyscallN`, costs 70 to 100 ns a call and has none of those limits.
  - A draw costs about 1 µs on the desktop: Sponza takes 0.3 ms to issue and 0.9 ms to draw, 10,000 separate draws 10.5 ms, and 100,000 instanced cubes 3.1 ms. So about 2,000 draws a frame, and instancing for more.
  - On the web, calling WebGL from Go for each draw costs 600 to 900 ns, and 10,000 draws took 41 ms; written into a command buffer, as GoLib's 2D already is, they took 13 ms. The 3D goes into that buffer, which also keeps it in order with the 2D. `gl.getError` took 61 µs, a round trip to Chrome's GPU process, so nothing reads from the graphics card while drawing.
  - Go decodes Sponza's pictures in 0.5 s on the desktop and 9.1 s in WebAssembly, which has one thread, and embedding them made a 52 MB `.wasm`: on the web the browser decodes pictures, and 3D assets are fetched beside the game instead of embedded.
  - Shots of the 3D repeat byte for byte on the desktop. The browser's differ from the desktop's by more than 8 levels on 1.16% of the pixels, at the edges of cut-out leaves and in the mipmaps: exact within a backend, a tolerance between them.
  - WebGL 2 in Chrome there renders into floating-point targets (`EXT_color_buffer_float`), which HDR needs, with anisotropic filtering and textures up to 16,384 pixels.
  - The 3D API goes in package `golib` (see [Decisions](#decisions)).

## Decisions

Open questions that have been answered, with the date and the reasons, so they aren't reopened by accident.

- **Framework distribution** (2026-09-16). GoLib ships as the whole template, with the framework's source inside, and games keep using it through `replace golib => ../../framework`. There is no published framework module, and the module path stays `golib`. Why: the CLI, `AGENTS.md` and the API guide describe one version of the framework, and a module updated on its own would get out of step with them; agents read the framework's code in `framework/`, not in the read-only module cache; and a published path, `github.com/pery77/golib/framework`, would be long and wouldn't match the package name. Releases, when there are any, will be tags of the whole repository. A game moves to a newer GoLib by copying its folder (see [architecture.md](architecture.md#distribution)). Reconsider if Go developers ask to use the framework outside the template; switching then means changing each game's `go.mod` and imports.
- **Libraries in shipped games** (2026-09-16). `golib dist` will put raylib and libffi next to the executable, with the third-party license notices, loaded the way debug builds load them, and zip that folder to share; a game will write nothing on the player's machine. Built on 2026-09-17, except on macOS (see M5). Why: raylib-go and ffi write their embedded libraries into cache folders named after their Go modules, shared with every other program built on them, and never check them again. A damaged copy, from an interrupted first start for example, stops the game from starting until someone deletes that folder, and the player sees no message: the libraries load before `main`, so `golib.Run` can't catch the error, and a Windows dist build has no console. Tried on 2026-09-16 with a truncated `raylib.dll` in the cache folder: the game exited with code 2, and the error went only to stderr. Programs that write DLLs into AppData and then load them also look like droppers to antivirus software. The cost: the executable no longer runs on its own, so players keep the folder together, which the zip takes care of. On Linux, the executable finds libraries in its own folder through an rpath, `$ORIGIN`; confirmed on 2026-09-18, when someone else's Linux dist build played from its unzipped folder. macOS doesn't look there for a library given by its bare name, so macOS builds keep the embedded copies until raylib-go can load a full path.
- **A finger is the mouse, and the desktop has no fingers** (2026-09-19). The oldest finger on a touch screen moves the mouse pointer and holds `MouseLeft` down, in package golib rather than in a backend, so `golib shot` plays it the same way. Games read fingers themselves only for what a mouse cannot do: controls held down, and two of them at once. On the desktop, `golib.PlayingWithTouch` is false and `Input.Touches` is always empty, even on a Windows laptop with a touch screen. Why: every menu and button already written for a mouse works by tapping, which is most of what a game needs on a phone, and a game gets that without a line of code; and raylib on the desktop fills its own touch point 0 from the mouse, so passing that on would make every click a finger, every computer report a touch screen, and every game draw its on-screen pads on a desktop. The cost: a game that wants a tap and a click to do different things cannot tell them apart, and a touch screen on a desktop is played with the mouse it moves. Reconsider if a game wants to be played with fingers on a Windows tablet, which would mean reading the system's touch behind raylib.
- **On-screen controls follow the player, not the machine** (2026-09-19). GoLib answers one question, `golib.PlayingWithTouch`: is the player playing with fingers right now? There is no "this machine has a touch screen" for a game to branch on. Why: one web build is opened on a phone and on a computer, and what a machine *can* do says nothing about how it *is* being used. A laptop with a touch screen and a mouse reports touch, and would get on-screen pads over its game; a phone needs them before the first finger has landed. So the first answer comes from the browser's own `pointer: coarse`, a finger being the main pointer, and after that the last thing used wins: a finger turns the controls on anywhere, and a key, the mouse or a gamepad turns them off again. A frame in which the player uses nothing changes nothing, so the controls don't blink between taps. The cost: a game cannot ask whether a touch screen exists at all, and a player who wants the pads while using a mouse needs the game to offer the choice, which `games/asteroids` does with F4. Reconsider if a game needs the capability itself, which would be one more call in the contract.
- **Tracker music and QOA stay off the web** (2026-09-18, amended 2026-09-19). A web build plays `.wav`, `.ogg` and `.mp3`, and nothing else. `.xm` and `.mod` music and `.qoa` sounds, which raylib reads on the desktop, are not decoded in the browser and are not going to be. What changed on 2026-09-19 is what happens then, for music only: GoLib plays a file of the same name in a format the browser reads when one sits beside the module, and lets the game run without the music when there is none, saying so on the console, where before it stopped the game with a message on the page. Why: a player who opens a link wants to play, and losing the music is a smaller loss than losing the game; the game's code stays the same on every platform, since it names the `.xm` and GoLib picks the file; and whoever builds the game hears about it while they build, not from a bug report. A `.qoa` sound still stops the game: a sound effect is chosen for a moment in the game, and silently playing another file for one would hide a mistake, where music is one long track a game can do without. `golib web` and `golib dist --web` name such files while they build, before anyone opens the page. Why: browsers decode sound through Web Audio, which reads the formats they ship with and nothing else; a tracker player or a QOA decoder would be a few thousand lines of Go, carried in every game that never uses one, for formats the web has no use for. The cost: `games/asteroids` and `games/skyraid`, whose music is `.xm`, play in a browser without their music until someone saves it as `.ogg` next to the module; their assets are left as they are, because that is their authors' call. Reconsider if someone wants tracker music in a browser badly enough to write the decoder, which would go in the framework, not the backend, since it would make samples both backends can play.
- **A web backend of GoLib's own** (2026-09-18). GoLib gets its own web backend, on WebGL 2 and Web Audio behind a small JavaScript file, reached through `framework/internal/device`; raylib is not built for the web with Emscripten. Why: Go compiles to WebAssembly by itself, so the zero-install promise holds, with no C toolchain for anyone and no 654 MB SDK for the maintainers; raylib-go has no web support and its maintainer doesn't plan any ([issue #356](https://github.com/gen2brain/raylib-go/issues/356)), and Raylib-Go-Wasm, the community fork, has no license, so its code can't be reused; an Emscripten build would mean publishing binaries into a repository whose value is that everything in it can be read, and copying between two separate memories. The fear that every feature would be built twice turned out to be smaller than it looked: the framework is 8,365 lines without tests, of which raylib touched about 320 call sites in 17 files, and 115 of those were tables of constants, so the contract is about 50 functions; the readers for Aseprite, Tiled, PNG, jfxr and the tunes, the camera, the vectors, the timers and the saved data are plain Go and are not touched. The recurring cost is real, though: anything added to the contract after this point costs two backends, which is why the web is decided before M7, 3D, starts. The cost: XM, MOD and QOA, and text in font files pixel for pixel as on the desktop (see [Web build](#web-build-started)). The seam landed first, on its own, with every game's screenshots byte for byte what they were, so the desktop build carries no risk from it.
- **2D and 3D** (2026-09-16). 2D first; 3D is its own milestone, M6, after M4 (M7, after the 2D essentials, since 2026-09-17), starting with glTF models from Blender, a 3D camera and basic lighting. Until then GoLib has no 3D. Why: 3D multiplies the API (cameras, models, lights, materials, 3D collisions), against "one obvious way" and "games, not engines"; agents reason about 3D space less reliably and can check it less reliably with `golib shot`; and 2D still lacks sprites, maps and fonts (M4) and a camera and vectors. Design those 2D pieces so that 3D can extend them later, `Vector2` next to a future `Vector3`, without breaking games. Superseded on 2026-10-20 by "3D is a full engine, in GoLib", below: 3D is no longer a small first scope.
- **Content formats** (2026-09-16). One format for each kind of content, the one the tool saves by default (see [architecture.md](architecture.md#content-established-tools-no-editors-of-our-own)):
  - Tiled: TMX maps and TSX tilesets only, not JSON. They are Tiled's defaults and what most tutorials and tile packs use, so saving in Tiled is enough; a second parser would double the code and the tests without letting agents do anything new, since they write TMX with CSV tile data as easily as JSON.
  - Aseprite: `.aseprite` files for animated sprites, with their tags as animations, and PNG for images and for sprite sheets on a grid, the usual form of free art packs. Not Aseprite's JSON sprite sheets: they need an export step that is easy to forget, and they would be a second way to do the same thing. The `.aseprite` format is documented and needs only `compress/zlib`; combining layers with their blend modes is the costly part.
  - Source files a game doesn't load, such as `.blend` or `.psd`, go in `games/<name>/sources/`, with the same paths as in `assets/`. They are committed, and `golib dist` leaves them out because it embeds only `assets/`.
  - 3D models, added on 2026-10-20 for M7: glTF (`.glb` and `.gltf`) and FBX, two formats for one kind of content, which this decision otherwise avoids. glTF is the open standard Blender exports, and GoLib reads it in Go; FBX is what Mixamo, most model stores and most other 3D tools give, and asking for every such file to go through Blender first would be the export step this decision keeps away. `golib build` turns FBX into GoLib's own model data, so games load both the same way. Skies and image-based light come from HDRI files (`.hdr`).
- **CLI in Go** (2026-09-16). The command logic moves from the twin scripts into one Go program, `tools/cli`, one command at a time, starting with `dist`, before dist builds become a folder and a zip; `tools/shipping` becomes part of it. The scripts keep what must work without Go, or while the CLI isn't running: downloading and checking Go in `setup`, building and starting the CLI, `clean` (on Windows a running program can't delete its own folder), the checks of `doctor` that don't need Go, and a message to run `setup` first. Done on 2026-09-17, starting with `dist` (see M5). Added the same day: `go` stays in the scripts too, so it still works when `tools/cli` doesn't compile. Why: two scripts of about 800 lines each, which must change together, have already drifted apart (only `golib.ps1` adds the icon and version information, and `golib.sh` has never run on Linux or macOS). Go gives one implementation for every platform, tested with `go test`, with a standard library for what the next changes need, such as zip files: Windows PowerShell 5.1's `Compress-Archive` writes their paths with backslashes (checked on 2026-09-16), and Linux can't make them without installing `zip`. The cost, measured on Windows: today `golib` spends about 420 ms starting PowerShell, checking that the built CLI is up to date adds about 100 ms, and building it the first time takes about 5 s. The vision's "short script" rule becomes short scripts to start, plain Go for the rest.
- **License** (2026-09-16). GoLib is under the zlib license, in `LICENSE`, with the copyright held by pery77. It covers the framework, the tools, the docs and the example games, except files with terms of their own, such as the music in `games/asteroids/assets/`. The games people make in `games/` are theirs to license. Why: the framework is compiled into every game, so its license decides what GoLib asks of whoever publishes one, and zlib asks nothing in binaries: only that the notice stays in source copies and that changed sources say so. It is raylib's license too, and common for game libraries. MIT would ask each game to carry GoLib's notice, and Apache-2.0 would add the license text and change notices. Since 2026-09-17 the framework also carries jfxr's synthesizer, under jfxr's BSD license, whose notice `golib dist` adds to every game (see Sound effects tool, below).
- **Sound effects tool** (2026-09-17). Sound effects are designed in jfxr, and games load its `.jfxr` files, from which `golib.NewSoundFile` makes the sound as jfxr does; GoLib gets no sound editor of its own. Why: the owner wanted filters like jfxr's, and a visual tool to make sounds by ear, saved in files that games load. An editor of GoLib's own would go against "no editors of our own" ([vision.md](vision.md)), and jfxr already is that tool: free, in the browser, with nothing to install, and its library exists to make sounds from `.jfxr` files inside games. Its files are JSON, with settings in seconds, Hz and percentages, so agents can write them and people can adjust them in jfxr, as with Tiled maps. Its synthesizer hasn't changed since 2019, so the format is stable, and its noise starts from a fixed seed, so a game can sound exactly like jfxr, and tests can check that. Also considered: rFXGen (zlib, by raylib's author, maintained, on the web and the desktop), whose `.rfx` files are binary, with settings from 0 to 1 and no units, four waveforms and no bit crush, and whose synthesizer comes from sfxr (MIT), so games would carry a notice anyway; Bfxr2 (MIT), in beta, which renamed its settings in 2025 and makes different noise on every render; jsfxr (sfxr.me, Unlicense, a port of sfxr), whose free version saves no files and whose noise also differs every time; and ZzFX (MIT), whose sounds are lines of code, not files, and change a little on every play. The cost: jfxr's BSD 3-Clause license asks for its notice in every game, which `golib dist` adds. jfxr's code is open, so if its website went away it could be hosted again, and GoLib would keep reading the files anyway.
- **2D essentials before 3D** (2026-09-17). With M5 done on Windows, and the other platforms on hold, the next milestone is M6, 2D essentials: vectors and a 2D camera, saved data, and looping sounds, starting with test games made from single prompts; 3D moves to M7. Why: nearly every 2D game needs those pieces, and today an agent works around each one by hand, while few games need 3D; the decision on 2D and 3D already asked for a camera and vectors designed so that 3D could extend them, which means building them first; and test games show what agents actually miss, so the order of the work comes from them rather than from guesses.
- **3D is a full engine, in GoLib** (2026-10-20). M7 builds a 3D engine inside GoLib, on raylib, for good-looking 3D games: models from glTF and FBX, skeletal animation, PBR materials and shaders of the game's own, lights and shadows, baked global illumination, physics and a character controller (see [M7](#m7-3d-planned)). It replaces the first scope of "2D and 3D", and changes three principles in [vision.md](vision.md): "games, not engines" becomes "games first", the dependency surface takes in GoLib's native library, and physics leaves the list of what is not planned. Why: the maintainers want to make good 3D games with GoLib, and models, a camera and basic lighting don't make one; raylib gives the parts (OpenGL through rlgl, examples of PBR, shadow maps, deferred rendering and GPU skinning) but no engine, so a good-looking 3D game on it means writing one, and writing it once in GoLib is better than once in every game. Also considered, on 2026-10-20: Godot 4.7, driven from Go through graphics.gd, as a separate project, which has a higher ceiling today (an editor, FBX, SDFGI, the groundwork of ray tracing on Vulkan) but leaves GoLib's tooling, its agent loop and its web backend behind, and depends on a young binding with few maintainers; Kaiju, a Go engine on Vulkan, still in heavy development and without the web; and a renderer of GoLib's own on WebGPU, years of work before the first game. The cost: the framework will grow to perhaps two or three times its size, with an API that has to stay small on top; agents reason about 3D space less reliably and check it less reliably by eye, which stage 8 answers with debug views and the scene as JSON; and the ceiling is a good-looking indie game, not the latest console's.
- **A GPU contract, and the engine above it** (2026-10-20). The 3D engine is plain Go in the framework, above a contract of about 30 functions at the level of a graphics card (buffers, textures, framebuffers, shaders, draws), implemented with rlgl on the desktop and WebGL 2 in a browser. raylib's models, animations and default shaders are not used. Why: the engine is written once and runs on both backends, where a contract at the level of "draw this model" would mean writing the 3D twice; WebGL 2 and OpenGL 3.3 are close enough that the web backend translates calls rather than reimplementing anything; shaders that are GoLib's own on both sides keep the shots of the two backends close, as they are in 2D; and raylib's `LoadModel` reads only a path on disk, while a dist build carries its assets inside the executable and writes nothing on the player's machine. The cost: GoLib writes what raylib already has (a model reader, skinning, animation), and every call in the contract is written twice.
- **Lightmaps hold the bounce, not the sun** (2026-10-26). A lightmap holds the sky's light, glowing materials' and area lamps', and only what the sun and the point and spot lamps bounce; GoLib draws those lamps' direct light each frame, with their shadows, from the same lamps the file exported. Why: things that move must be lit and must shade the level as it is drawn, which light baked whole can't do without a second map of shadows (Unity's "baked indirect" makes the same choice); and the same lamps light the level and what moves in it, so they match. The cost: the sun and lamps are drawn each frame, and a level whose lamps are many needs them within GoLib's 8 a pass; lamps that light only the level could be baked whole later, with a custom property.
- **Rigid bodies with Jolt, released from the fork first** (2026-10-24, carrying out the native library decision below). Jolt is the physics engine, as decided, rather than a simulation in Go: stacking, friction, sleeping and continuous collision are years of work that Jolt has done, and the user asked for what works best rather than a new wheel. The native library holds Jolt alone. JoltPhysics.js, Jolt's author's own WebAssembly build, published on npm under MIT, is the browser's copy, downloaded by setup from jsDelivr at a pinned version and checksum rather than built by GoLib. The workflow publishes releases of the repository it runs in; `nativeRepository` points at the fork, supercanocoder/golib, until the main repository makes its own, and changing it is one line. Builds carry the library only when the game uses rigid bodies, found by a marker the linker keeps only then, so games without them ship and test exactly as before. Characters stay GoLib's controller in Go, with a kinematic capsule in Jolt, the way Jolt's own `CharacterVirtual` uses an inner body, rather than Jolt's controller, so they behave the same with and without rigid bodies, and in tests without the library.
- **FBX read in Go** (2026-10-24, amending the next decision and "Content formats" above). FBX files are read in Go, in `framework/internal/fbx`, by `golib.NewModel` when the game loads them, as glTF files are, into the same document; ufbx and `golib build`'s conversion are not used, and the native library keeps Jolt alone. Why: a binary FBX file is a tree of records with zlib-compressed arrays, and what games need of it (meshes, materials, skins, blend shapes, takes, and FBX's transforms with their pivots and pre-rotations) came to about 1,700 lines of plain Go; it needs no binaries, no continuous integration and no download in `golib setup`, it works in a browser, where a web build reads the file as the desktop does, and it can be read and fixed like the rest. Checked against the same scene exported from Blender as glTF and as FBX, which pose within two millimeters. The cost: ufbx's years of fixes for unusual files are not there, so FBX saved as text, files older than FBX 7.1 (2011), cameras, lights, in-between shapes and second animation layers are refused or left out, and odd exporters may need a fix found by a game; a dist build carries the FBX reader, about the size of the glTF one, and decodes the file at load time rather than at build time. Reconsider if games keep hitting FBX files GoLib reads wrong, with ufbx in the native library that Jolt brings anyway.
- **A native library of GoLib's own** (2026-10-20). GoLib gets a shared library of its own, built from source in the repository by continuous integration for each platform, downloaded by `golib setup` into `.tools/` with a checksum, as Go is, copied next to builds as raylib is, and called through purego. It holds ufbx, the FBX reader Godot uses since 4.3, and Jolt, the physics engine. Nobody needs a C compiler, players included. Why: FBX is a large, partly undocumented format, and a reader in Go would be a project of its own, while ufbx is one C file, MIT or public domain, and well tested; Jolt is the physics engine Godot and Horizon Forbidden West use, MIT, and deterministic, which `golib shot` needs. Neither has a Go version worth the name. FBX is turned into GoLib's own model data when the game is built, so dist and web builds don't carry ufbx, and in a browser Jolt comes from JoltPhysics.js, its own WebAssembly build. The cost: a CI and release process for binaries, which GoLib doesn't have yet; binaries in a project whose value is that it can be read, which their source in the repository and a build anyone can repeat answer; and two more notices in every dist build that uses them. This amends rule 4 of [AGENTS.md](../AGENTS.md#golden-rules), with this decision as the approval.
- **3D in the browser too** (2026-10-20). Every stage of M7 lands on the desktop and in a browser at once, with a Web quality preset where WebGL 2 or WebAssembly can't keep up. Why: a link anyone can open, and itch.io, are part of GoLib's promise, and the GPU contract makes the web backend's share of each stage small. The cost: rendering into floating-point targets needs `EXT_color_buffer_float`, which nearly every browser has; WebAssembly is slower than native code, so the Web preset gives up some effects; and every 3D feature has to be checked in both places.
- **OpenGL 3.3 and WebGL 2 are the floor** (2026-10-20). Nothing GoLib's 3D needs uses compute shaders or anything else above OpenGL 3.3 and WebGL 2. Why: macOS stops at OpenGL 4.1, browsers at WebGL 2, and raylib-go's libraries are built for OpenGL 3.3; a game that looks right on one machine has to look right on all of them. The cost: effects that want compute shaders, such as particles simulated on the graphics card, are done another way or wait for a newer backend.
- **The 3D API lives in package `golib`** (2026-10-20, opened and answered the same day, in M7's stage 0). `Vector3` next to `Vector2`, `Camera3D` next to `Camera`, and the 3D pass opened from the `Screen` a game already draws on, with one import. Large parts that games never name, such as the glTF reader or the bounding volume hierarchy, may live in `framework/internal/`. Why: games reach the 3D through what they already use (`Screen`, `Input`, `Color`, `ReadAsset`), and a package `golib/world` would import `golib` while `Screen` needed to reach into it, which Go's packages can't do both ways without exported hooks no game should see; agents guess `golib.Something` and are right, where a second package is one more thing to guess. The cost: package `golib` grows by perhaps 100 to 150 names, and the API guide with it, which a 3D part of its own keeps readable. Also considered: a package of its own, `golib/world`, which keeps the 2D guide as short as it is.
- **No ray tracing in real time; baked light instead** (2026-10-20). GoLib's 3D has no real-time ray tracing. Light is baked in Blender with Cycles, a ray tracer, into lightmaps and probes that games load, and screen-space reflections stand in for ray-traced ones. Why: OpenGL and WebGL have no ray tracing, which needs Vulkan, Direct3D 12 or Metal; even Godot 4.7 has only the groundwork of it. Reconsider with a Vulkan or WebGPU backend, after M7.
- **Where saved data goes** (2026-09-17). `golib.SaveData` writes, in a dist build, to a folder named after the game inside a folder named `GoLib games` in the player's settings folder (`%AppData%` on Windows, `~/.config` on Linux, `~/Library/Application Support` on macOS); in a debug build, to `build/<game>/save/`, next to the executable; under `golib shot` and in tests, nowhere: data stays in memory. Why: the folder a player unzipped the game into may be read-only, and settings folders are where programs keep such data; `GoLib games` keeps games from writing into another program's folder with the same name, such as `crates`, and shows the player where the data came from; the game's folder name, passed by `golib dist`, doesn't change when a player renames the executable; making a game writes nothing outside the project, and `golib clean` resets it; shots and tests repeat only if they start with nothing saved, and write nothing. The cost: data saved while making a game isn't where the shared game looks for it, and two published games with the same folder name would share a save folder.
